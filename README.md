# 五子棋 AI 实验：v1 → v2 → v3 的三次迭代，以及一个被数据否掉的方案

一个 15×15 五子棋 AI 的完整优化过程记录。重点不是"我做了一个很强的 AI"——它并不强，
而是一次改动到底有没有让 AI 变强，以及**怎么用实验证明它没变强**。

结论先行：

| 版本 | 改动 | 关键局面 | 对 v1 战绩（黑白互换 4 局） | 单步最长 | 是否采用 |
|---|---|---|---|---|---|
| v1 | 连续子计数 + 单层贪心 | 6/7 | —（基准） | ~0.005 s | — |
| **v2** | **九格窗口 + 棋形模板匹配** | **7/7** | **4 胜 0 平 0 负** | ~0.005 s | ✅ |
| v3 | v2 + 冲四搜索 + 两层前瞻 | 7/7 | 3 胜 0 平 1 负 | 0.4 ~ 0.9 s | ❌ |

v3 与 v2 直接对抗：**0 胜 1 平 3 负**，慢两个数量级还更弱，因此没有采用。

> 耗时受机器负载影响：同一份代码两次实测的 v3 单步最长分别是 0.925 s 与 0.671 s。
> 胜负与手数是稳定的，两次完全一致；绝对耗时只用来判断数量级。

---

## 一、起点：v1 输在具体的一手棋上

v1 的策略很朴素：对每个空位算分，分数 = 自己的连续子价值 + 0.85 × 对手的连续子价值，取最高分落子。
纯 1 层贪心，不做任何搜索。

它在第 2 局第 28 手（执白）输了。当时的局面：

```
黑方 F 列：X X . X     ← 中间那一点补上就是活四
```

正解是占住 F7 化解。v1 却下了 G6，去做自己的四连。黑方随即补 F7 成活四，白方三手内被五连。

**为什么它会选错？** 因为 v1 的棋形只有"连续同色棋子个数"这一种表示：

- 活四（两端全空，挡不住）= 4 连 → 1000 分
- 冲四（一端被堵，能挡）= 4 连 → 1000 分

两者分数完全相同。v1 给 G6 算了 1008 分、给 F7 算了 851 分，于是选了 1008。
它根本不知道"自己做一个冲四"和"对手马上要活四"是两件严重程度差一个量级的事。

**根因**：棋形的性质由一整段格子决定（有没有空隙、两端是否被堵），
用"连续个数"来表示，这些信息全丢了。

---

## 二、v2：只改"棋形怎么表示"

v2 相对 v1 只动一个地方，保持单变量对照：

以落点为中心取 **9 格窗口**（左 4 + 自身 + 右 4），把窗口串成字符串，
再用模板去匹配这一条线到底是什么棋形：

```
五连 > 活四 > 冲四 > 活三 > 眠三 > 断点 ...
```

于是"活四"和"冲四"、连着的和隔开的，终于能区分开。再补两条硬规则兜底（先判对错，再谈好坏）：

1. 我能一步成五 → 直接下
2. 对手能一步成五 → 必须堵

上面那个局面，v2 会正确地去占 F7。

改进后的验证不是"看着像更好了"，而是可复现的实验（见第四节）：7 个有唯一正解的关键局面
v1 对 6 个、v2 全对；对基准 v1 黑白互换 4 局，v2 四局全胜，平均 31 手。

---

## 三、v3：加了搜索，结果更差 —— 这是本项目最有价值的一节

v2 仍然偏防守，自战经常和棋。很自然的想法是：光看"这一手值多少"不够，
应该看"下完这一手之后对手还能拿到什么"，也就是把 1 层贪心升级成 2 层前瞻（minimax）。

v3 加了两样东西：

1. **冲四连击（VCF）**：靠连续的强制手把对手逼死
2. **两层前瞻**：对自己的候选点做一层对手最优应对的推演

结果**反而全面变差**：

| 对局 | 结果 | 单步最长 |
|---|---|---|
| v3 vs v1（4 局，黑白互换） | 3 胜 0 平 1 负 | 0.7 ~ 0.9 s |
| v3 vs v2（4 局，黑白互换） | **0 胜 1 平 3 负** | 0.3 ~ 0.5 s |

而且慢了两个数量级（v2 是 0.005 s 级）。

**为什么会这样？** 因为 minimax 的正确性依赖评估函数本身准确。
v2 的棋形评分是个**手工调出来的启发式**，它对自己的判断有系统性偏差；
在 1 层时这种偏差只是"偶尔选错"，套进 2 层 minimax 后，
偏差会被"对手最优应对"这一步放大——AI 开始为了规避一个并不存在的威胁而放弃实际收益。

在评估函数还没校准之前就上搜索，是在放大误差而不是减少误差。
所以 v3 被否掉，项目停在 v2。

> 这一节之所以留在仓库里，是因为**能被数据否掉的方案记录，比只展示成功案例更有信息量**。
> 如果只放 v2，看的人无从判断"架构演进"是设计出来的还是碰到运气。

## 四、实验方法

实验台在 `lab/` 下，三部分：

### A. 关键局面测试（7 题，每题只有唯一正解）

不是随机开局，而是手工构造"只有一手正确"的局面，用来精确测某个能力在不在：

| 局面 | 能力 |
|---|---|
| P1 自己一步成五 | 收杀 |
| P2 对手一步成五 | 必堵 |
| **P3 对手活四成点** | **区分活四/冲四（v1 就死在这）** |
| P4 自己做活四 | 主动进攻 |
| P5 跳四必堵 | 看得见空隙 |
| P6 双活三 | 双威胁 |
| P7 空盘开局 | 开局合理性 |

### B. 同条件对战

固定基准 v1，**黑白互换**（消除先手优势），两种开局，同一 3 秒/步限制。
不是"跑几局看看"，而是每个对位都对称跑两局。

### C. 接口自测（13 项）

引擎必须满足的硬约束，逐条检查而不是靠人眼看：

- 不修改输入棋盘（30 个随机局面，0 次被改）
- 返回值一定落在空位（30 个随机局面，0 次非法）
- 单步 3 秒内、每方每局累计 60 秒内
- 导入时不弹窗、不阻塞、无副作用
- 整局无异常无超时

## 五、目录

```
gomoku-ai-lab/
├─ gomoku_v1.py        v1：连续子计数 + 单层贪心（对照基准）
├─ gomoku_v2.py        v2：九格窗口棋形模板 + 必胜必堵（最终采用的版本）
├─ gomoku_v3.py        v3：v2 + 冲四搜索 + 两层前瞻（实测更差，未采用）
├─ gomoku_gui.py       人机对弈界面，界面上可直接切换 v1/v2/v3
├─ lab/
│   ├─ engine_lab.py   对照实验台内核：任意两个 AI 摆盘对下，校验合法性、计时、记谱
│   ├─ run_lab.py      实验主程序：跑 A+B+C 三部分并输出数据
│   ├─ selftest.py     接口自测（13 项）
│   ├─ gui_source.py   界面源码
│   ├─ gui_smoke.py    界面冒烟测试：自动下完整一局
│   ├─ make_shots.py   生成关键棋局示意图（不依赖屏幕）
│   └─ results/        实验输出：results.json + 结果汇总.md
└─ screenshots/        关键棋局截图
```

三个引擎都只暴露一个入口，界面与策略完全解耦：

```python
def get_move(board, player) -> (row, col)
```

`board` 是 15×15 的二维列表，`"."` 空位、`"X"` 黑、`"O"` 白。

## 六、跑起来

只依赖 Python 标准库，无需安装任何第三方包。

```bash
# 人机对弈（可切换 v1/v2/v3 与执黑执白，支持悔棋、截图、导出棋谱）
python gomoku_gui.py

# 复现全部实验数据（A 关键局面 + B 对战 + C 用时统计）
python lab/run_lab.py

# 只跑接口自测
python lab/selftest.py
```

单独调用引擎：

```python
import gomoku_v2
board = [["."] * 15 for _ in range(15)]
print(gomoku_v2.get_move(board, "X"))   # -> (7, 7)  空盘走天元
```

## 七、已知不足

- **v2 仍偏防守**，自战常成和棋，主动进攻的收益估计不足
- 评估函数是手工调的权重，没有做参数寻优或学习
- v3 的失败说明"上搜索"这条路的**前提**（评估函数已校准）没满足，
  真正的下一步应该是先把 v2 的评分权重调准，再考虑搜索，而不是直接叠 minimax
- 没有做置换表、迭代加深等工程优化，v3 的耗时高除了搜索本身也有这部分原因
